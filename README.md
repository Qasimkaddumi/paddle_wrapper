# paddle_wrapper

A type-safe Flutter wrapper for [Paddle Billing](https://www.paddle.com/) (Paddle.js v2). Open overlay or inline checkouts, listen to checkout events, show localized prices, run Paddle Retain flows, and wait for your backend to confirm a payment, all from Dart.

## Features

- Overlay checkout (Paddle's default UI) and inline checkout inside your own layout.
- `PaddleCheckoutBuilder`: build your own order summary from live checkout data.
- Typed checkout events (`CheckoutEvent`, `CheckoutEventName`).
- Prefill customer, discount, custom data, and open existing draft transactions.
- Localized price previews and transaction previews.
- Paddle Retain: cancellation flows and demos.
- `PaymentConfirmation`: poll your backend until an order is final, with a configurable `PollingPolicy`.
- Saved payment methods (with a customer auth token generated by your backend).
- A typed exception hierarchy rooted at `PaddleException`.

## How it fits

```text
 Flutter web app ----opens----> Paddle checkout (Paddle.js) ----pays----> Paddle
        |                                                                   |
        |                                          webhook: transaction.completed
        |                                                                   v
        +------ polls order status (PaymentConfirmation) ------> YOUR backend
```

1. Your app opens a checkout with `Paddle.instance.checkout.open` or `PaddleCheckoutFrame`.
2. The customer pays inside Paddle's checkout. Paddle.js emits `checkout.completed` in the browser.
3. Paddle sends a webhook to **your backend**. Your backend marks the order as paid.
4. Your app polls **your backend** with `PaymentConfirmation` until the order is final.

The package never holds API keys and never receives webhooks. It only talks to Paddle.js in the browser and to the functions you pass in.

## Platform support

Flutter **web only** for now. Paddle.js runs in the browser. On other platforms, every call throws `PaddleUnsupportedPlatformException`. The package is structured so that other platforms can be added later by implementing `PaddlePlatform`.

## Setup in Paddle

1. **Client-side token.** In Paddle, go to **Developer tools > Authentication** and create a client-side token. Sandbox tokens start with `test_`, production tokens with `live_`. This token is safe to ship in a web app.
2. **Approved domain.** Go to **Checkout > Checkout settings** and add your app's origin (for example `http://localhost:5000` during development, and your production domain) as an approved domain for payment links. Paddle rejects checkouts opened from origins that are not approved.
3. **Default payment link.** Set a default payment link on the same settings page.
4. **Prices.** Create the prices you sell in the catalog. Use their IDs (`pri_...`) in your app.

Never use a Paddle API key (`pdl_...`) in the app. `Paddle.initialize` rejects those tokens.

## Quick start

Initialize once, before `runApp`:

```dart
import 'package:flutter/widgets.dart';
import 'package:paddle_wrapper/paddle_wrapper.dart';

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await Paddle.initialize(
    const PaddleConfig(clientToken: 'test_xxx'),
  );
  runApp(const MyApp());
}
```

Open an overlay checkout from a button:

```dart
await Paddle.instance.checkout.open(
  const CheckoutOptions(
    items: [CheckoutItem(priceId: 'pri_xxx')],
    settings: CheckoutSettings.overlay(theme: CheckoutTheme.light),
  ),
);
```

`Paddle.initialize` is safe to call more than once. Later calls return the existing instance. Use `Paddle.isInitialized` to check, and `Paddle.instance` to read it (it throws `PaddleNotInitializedException` before initialization).

## Inline checkout (design your own checkout page)

An inline checkout is rendered into your page by `PaddleCheckoutFrame`. Give it a bounded height:

```dart
SizedBox(
  height: 650,
  child: PaddleCheckoutFrame(
    options: const CheckoutOptions(
      items: [CheckoutItem(priceId: 'pri_xxx')],
      settings: CheckoutSettings(variant: CheckoutVariant.onePage),
    ),
  ),
)
```

Paddle requires that an inline checkout shows the items and totals on your page, so you can design the summary yourself. `PaddleCheckoutBuilder` rebuilds your UI from the live checkout state:

```dart
PaddleCheckoutBuilder(
  onEvent: (event) {
    if (event.isCompleted) {
      // Confirm with your backend before granting access. See below.
    }
  },
  builder: (context, state) {
    final data = state.data;
    return Column(
      children: [
        for (final item in data?.items ?? const <CheckoutDataItem>[])
          Text('${item.priceName} x ${item.quantity}'),
        Text('Total: ${data?.totals?.total ?? '-'} ${data?.currencyCode ?? ''}'),
        if (state.error != null) Text(state.error!.detail ?? 'Checkout error'),
      ],
    );
  },
)
```

`CheckoutState` gives you `phase` (`idle`, `ready`, `processingPayment`, `completed`, `closed`), `data`, `lastEvent`, and `error`.

The card form itself is always rendered by Paddle inside the frame. Card details never reach your app, which keeps you out of PCI scope for card data.

Change items on an open checkout with `Paddle.instance.checkout.updateItems`, or apply a discount or customer data with `Paddle.instance.checkout.update`:

```dart
Paddle.instance.checkout.updateItems([
  const CheckoutItem(priceId: 'pri_xxx', quantity: 2),
]);

Paddle.instance.checkout.update(
  CheckoutUpdate(
    items: const [CheckoutItem(priceId: 'pri_xxx', quantity: 2)],
    discount: const CheckoutDiscount.code('LAUNCH20'),
  ),
);
```

If you change `options.items` on a `PaddleCheckoutFrame`, the frame sends the new items to the open checkout. Re-opening with different settings is not supported; give the widget a new `key` instead.

### Customizing the checkout

`CheckoutSettings` maps to Paddle.js settings. Every field is optional. Unset fields keep Paddle's default, or the default you set with `PaddleConfig.checkoutSettings`.

```dart
const CheckoutSettings(
  theme: CheckoutTheme.dark,
  locale: CheckoutLocale.de,
  variant: CheckoutVariant.multiPage,
  allowedPaymentMethods: [PaymentMethod.card, PaymentMethod.paypal],
  showAddDiscounts: false,
  showAddTaxId: true,
  allowLogout: false,
  allowDiscountRemoval: false,
)
```

- `theme`: `CheckoutTheme.light` or `CheckoutTheme.dark`.
- `locale`: `CheckoutLocale` values such as `CheckoutLocale.en`, `CheckoutLocale.ptBR`.
- `variant`: `CheckoutVariant.onePage` (required for upsells), `multiPage`, or `express` (inline only).
- `allowedPaymentMethods`: a list of `PaymentMethod`. `PaymentMethod.unknown` is not allowed.
- `showAddDiscounts`, `showAddTaxId`, `allowLogout`, `allowDiscountRemoval`, `showNonExpressPaymentMethods`.
- `successUrl`: a `Uri` (http or https) to redirect to after payment.
- `frameStyle` and `frameInitialHeight` for inline frames. Use the `frameStyle` parameter of `PaddleCheckoutFrame` or `CheckoutSettings.inline`.

Use `CheckoutSettings.overlay(...)` for overlay checkouts and `CheckoutSettings.inline(frameTarget: ...)` when you need the inline factory. To change defaults for every checkout at runtime, call `Paddle.instance.updateCheckoutSettings(settings)`.

Give each inline frame a unique `frameTarget` (the default is `paddle-checkout-frame`) when you show more than one on a page.

## Prefilling customer, discount and custom data

```dart
CheckoutOptions(
  items: const [CheckoutItem(priceId: 'pri_xxx', quantity: 2)],
  customer: CheckoutCustomer.email(
    'buyer@example.com',
    address: CheckoutAddress.details(countryCode: 'US', postalCode: '10001'),
  ),
  discount: const CheckoutDiscount.code('LAUNCH20'),
  customData: const {'userId': 'user_123'},
)
```

- `CheckoutCustomer.id('ctm_...')` uses an existing Paddle customer. `CheckoutAddress.id` and `CheckoutBusiness.id` use saved records.
- `CheckoutDiscount.id('dsc_...')` applies a discount by Paddle ID instead of code.
- **`customData` is how you link a Paddle transaction to your own user or order.** Whatever you put there comes back in the webhooks Paddle sends to your backend (`data.custom_data`). Put your own identifiers in it, such as `userId` or `orderId`, so your backend knows which account to update. Never put secrets in it.

## Opening a checkout for an existing transaction

If your backend already created a draft transaction (`txn_...`), open that instead of items:

```dart
await Paddle.instance.checkout.open(
  const CheckoutOptions.transaction(
    'txn_xxx',
    settings: CheckoutSettings.overlay(),
  ),
);
```

Items and a transaction ID are mutually exclusive. Passing both throws `PaddleConfigurationException`.

## Events

Every checkout event is available on one stream:

```dart
final subscription = Paddle.instance.events.listen((event) {
  switch (event.name) {
    case CheckoutEventName.completed:
      final transactionId = event.data?.transactionId;
      // Start confirmation with your backend. See below.
    case CheckoutEventName.closed:
      // The buyer closed the checkout.
    case CheckoutEventName.error:
    case CheckoutEventName.paymentError:
    case CheckoutEventName.warning:
      final detail = event.error?.detail ?? event.error?.code;
      // Show or log `detail`.
    default:
      break;
  }
});
```

`Paddle.instance.checkout.events` is the same stream. Helper getters are available too: `isCompleted`, `isClosed`, `isLoaded`, and `isError`.

Known names are `CheckoutEventName` values: `loaded`, `updated`, `closed`, `completed`, `paymentInitiated`, `paymentSelected`, `paymentFailed`, `paymentError`, `itemsUpdated`, `itemsRemoved`, `discountApplied`, `discountRemoved`, `customerCreated`, `customerUpdated`, `customerRemoved`, `upsellCanceled`, `error`, `warning`. Names the package does not know yet map to `CheckoutEventName.unknown`, and the original name stays in `event.rawName`.

Cancel the subscription in `dispose` as usual.

## Confirming payment with your backend

The `checkout.completed` event only means that Paddle.js finished in the browser. It does not mean that the order is paid in your system. The payment is confirmed by the `transaction.completed` webhook that Paddle sends to **your server**. That webhook can arrive a few seconds after the browser event, or not at all if the buyer closes the tab.

**Never grant access based only on client events.** Wait for your backend.

`PaymentConfirmation` polls a function that you supply (typically an HTTP call to your own API). The package performs no HTTP:

```dart
// OrderStatus is your own type, returned by your own API client.
final confirmation = PaymentConfirmation<OrderStatus>(
  fetchStatus: myApi.getOrderStatus,          // Future<OrderStatus> Function(String)
  isFinal: (status) => status.isFinal,         // true once paid or failed
  policy: const PollingPolicy(
    initialInterval: Duration(seconds: 2),
    maxInterval: Duration(seconds: 10),
    timeout: Duration(minutes: 2),
  ),
);

try {
  final status = await confirmation.waitFor(transactionId);
  if (status.isPaid) {
    // Grant access.
  }
} on PaymentConfirmationTimeoutException catch (error) {
  // Still processing. Tell the user and check again later.
}
```

- `waitFor(transactionId)` completes with the first final status.
- `watch(transactionId)` returns a `Stream<T>` of every status, which is useful to show progress.
- `PollingPolicy` controls the delay (`initialInterval`, `maxInterval`, `backoffFactor`), the total budget (`timeout`), an optional `maxAttempts`, and whether a failed fetch is retried (`retryOnError`).

## Localized pricing

Show prices in the visitor's currency and locale, with tax, before any checkout opens:

```dart
final prices = await Paddle.instance.pricing.previewPrices(
  const PricePreviewRequest(
    items: [
      PricePreviewItem('pri_xxx'),
      PricePreviewItem('pri_yyy', quantity: 2),
    ],
  ),
);

final line = prices.lineItemFor('pri_xxx');
final unitPrice = line?.formattedUnitTotals?.total; // e.g. "$10.00"
```

Without an `address` or `customerIpAddress`, Paddle localizes the prices from the visitor's IP address. Pass `PreviewAddress(countryCode: 'DE')` in `address` to choose the location yourself.

To show the exact totals for a cart, including tax and discounts, use `previewTransaction`:

```dart
final preview = await Paddle.instance.pricing.previewTransaction(
  const TransactionPreviewRequest(
    items: [TransactionPreviewItem('pri_xxx', quantity: 2)],
    customerId: 'ctm_xxx',
  ),
);

final total = preview.totals?.total; // amount in the lowest denomination, as a string
```

Preview requests are validated locally. Invalid requests throw `ArgumentError`.

## Paddle Retain

Retain runs cancellation flows and salvage offers. It only loads for **live** accounts, and the customer must be identified with a `ctm_...` ID.

```dart
await Paddle.initialize(
  const PaddleConfig(
    clientToken: 'live_xxx',
    retainCustomerId: 'ctm_xxx',
  ),
);

// When the customer logs in or out later:
Paddle.instance.updateRetainCustomer('ctm_xxx');
Paddle.instance.updateRetainCustomer(null);

final result = await Paddle.instance.retain.initCancellationFlow(
  subscriptionId: 'sub_xxx', // required when the customer has several subscriptions
);

if (result.wantsToCancel) {
  // Cancel the subscription on your side or in Paddle.
} else if (result.wasRetained) {
  // The customer accepted an offer.
}
```

`Paddle.instance.retain.demo(RetainDemoFeature.cancellationFlow)` shows a Retain demo for development.

## Saved payment methods

To let a returning customer pay with a saved card, your backend creates a customer auth token for that customer through the Paddle API. Your app passes the token and the saved payment method ID (`paymtd_...`) to the checkout:

```dart
CheckoutOptions(
  items: const [CheckoutItem(priceId: 'pri_xxx')],
  customerAuthToken: authTokenFromYourBackend,
  savedPaymentMethodId: 'paymtd_xxx',
)
```

`savedPaymentMethodId` requires `customerAuthToken`, and it cannot be used with the express variant. Both values come from your backend. Do not generate or store the token in the app.

## Error handling

Every error from this package extends `PaddleException`, which has a `message`:

| Exception | When |
| --- | --- |
| `PaddleNotInitializedException` | `Paddle.instance` is used before `Paddle.initialize` completes. |
| `PaddleConfigurationException` | An input is invalid, such as an empty token, a `pdl_` key, or items with a transaction ID. Thrown before any call to Paddle.js. |
| `PaddleUnsupportedPlatformException` | Used on a platform other than web. |
| `PaddleScriptLoadException` | Paddle.js could not be loaded, or timed out. |
| `PaddleJsException` | A Paddle.js call or promise failed. Has `type`, `code`, `detail` and `raw` when Paddle returned them. |
| `PaymentConfirmationTimeoutException` | Your backend did not confirm the order within the `PollingPolicy` budget. Has `transactionId`, `attempts` and `lastStatus`. |

```dart
try {
  await Paddle.initialize(const PaddleConfig(clientToken: 'test_xxx'));
} on PaddleConfigurationException catch (error) {
  // Fix the configuration.
} on PaddleScriptLoadException catch (error) {
  // Show "payments are unavailable right now".
} on PaddleException catch (error) {
  // Anything else from this package.
}
```

Checkout problems that Paddle reports during checkout (for example an invalid discount code) do not throw. They arrive as `checkout.error` or `checkout.warning` events, and `CheckoutState.error` holds the last one.

## Testing

Paddle.js is a browser global, so tests should not depend on it. Pass a `PaddlePlatform` to `Paddle.initialize` to replace the bridge with a fake:

```dart
await Paddle.initialize(
  const PaddleConfig(clientToken: 'test_xxx'),
  platform: MyFakePaddlePlatform(), // implements PaddlePlatform
);
```

`PaddlePlatform` is an interface with one method per Paddle.js call (for example `openCheckout` and `pricePreview`). Your fake records the JSON it receives and returns canned responses. The package's own tests use this approach.

Between tests, call `await Paddle.reset();` so the next `Paddle.initialize` starts from scratch. `reset` is marked `@visibleForTesting`.

## Security notes

- Use only the **client-side token** (`test_...` or `live_...`) in the app. It is public by design.
- **Never** put a Paddle API key (`pdl_...`) in the app. `Paddle.initialize` throws `PaddleConfigurationException` if it sees one, but that check is a safety net, not a substitute for keeping keys on the server.
- Never trust a `checkout.completed` event as proof of payment. Confirm the order with your backend after it receives the `transaction.completed` webhook. Verify webhook signatures on your server.
- `customData` travels through the browser. Store identifiers there, not secrets or permissions.

## Architecture

The package follows a feature-based, clean-architecture layout. Each feature has the same three layers, and the platform bridge sits underneath them all.

```text
lib/
  paddle_wrapper.dart                  barrel: the public API
  src/
    paddle.dart                        Paddle facade (singleton, events, services)
    paddle_config.dart                 PaddleConfig
    core/
      json.dart                        JSON helpers and enum parsing
      paddle_environment.dart          sandbox and production
      paddle_exception.dart            PaddleException hierarchy
      platform/
        paddle_platform.dart           PaddlePlatform: the Paddle.js bridge interface
        web/                           Paddle.js implementation (dart:js_interop)
        stub/                          non-web stub (throws unsupported)
    features/
      checkout/
        domain/                        CheckoutService, entities (options, items, events, state)
        data/                          PaddleCheckoutService
        presentation/                  PaddleCheckoutFrame, PaddleCheckoutBuilder
      pricing/
        domain/                        PricingService, previews
        data/                          PaddlePricingService
      retain/
        domain/                        RetainService, results
        data/                          PaddleRetainService
      confirmation/
        domain/                        PaymentConfirmation, PollingPolicy
```

- **Domain** holds the typed models and the service interfaces. It has no Paddle.js or Flutter web code.
- **Data** implements the services on top of `PaddlePlatform`. This is where typed models become Paddle.js JSON, and back.
- **Presentation** holds the Flutter widgets (`PaddleCheckoutFrame`, `PaddleCheckoutBuilder`).
- **Confirmation** has no data layer on purpose. It calls the fetch function you provide, so the package never makes HTTP requests of its own.
- **`PaddlePlatform`** is the extension point. A future mobile or desktop platform only needs a new implementation of that interface. The rest of the package stays as it is.
